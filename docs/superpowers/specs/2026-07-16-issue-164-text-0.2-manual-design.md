# bluetape4k-text 0.2 매뉴얼 설계

- 관련 이슈: [#164](https://github.com/bluetape4k/bluetape4k-text/issues/164)
- 대상 저장소: `bluetape4k/bluetape4k-text`
- 대상 브랜치: `develop`
- 작업 브랜치: `docs/text-0.2-manual`
- 문서 유형: Type E 유지보수

## 배경

현재 저장소에는 루트와 모듈별 README, 실행 가능한 예제, 품질 보고서, 벤치마크 결과가 흩어져 있다. 각 자료는 개별 기능을 확인하기에는 유용하지만, 처음 접한 사용자가 어떤 모듈을 선택하고 어떤 순서로 학습하며 운영 시 무엇을 조심해야 하는지 한 흐름으로 설명하지 못한다.

0.2 매뉴얼은 README를 확장한 긴 소개문이 아니다. 안정 배포본 `0.2.1`을 기준으로 기능 선택, 처리 흐름, 실행 예제, 품질 근거, 운영 계약을 연결하는 독립 문서 체계다. 이후 블로그나 사이트 소개 글은 이 매뉴얼을 참고하며, 매뉴얼이 라이브러리 사용법의 기준 문서가 된다.

## 목표

1. 안정 배포본 `0.2.1`에서 실제로 사용할 수 있는 기능만 설명한다.
2. 사용자가 문제에서 출발해 모듈, API, 예제로 자연스럽게 이동하도록 안내한다.
3. 한국어·영어 매뉴얼의 정보 구조와 기술 내용을 동등하게 유지한다.
4. README, 실제 소스, 테스트, 예제, 품질 보고서, 벤치마크를 추적 가능한 근거로 연결한다.
5. 저장소 안의 `docs/manual/`을 원본으로 삼고, 웹사이트는 검증된 산출물을 가져가 게시한다.
6. 버전, 문서 목록, 모듈 목록, 자산, 근거 자료를 기계적으로 검증할 수 있게 한다.

## 제외 범위

- `0.3.0` 마일스톤에 계획된 미배포 기능은 설명하지 않는다.
- 공개 API나 라이브러리 동작을 변경하지 않는다.
- 기존 README를 매뉴얼로 대체하거나 삭제하지 않는다.
- 블로그 글을 원본으로 삼지 않는다. 참고 자료가 있더라도 실제 소스와 테스트로 다시 확인한다.
- 이번 소스 저장소 PR에서 웹사이트 코드를 함께 바꾸지 않는다.
- 문서만 바꾸므로 Gradle/JVM 모듈 테스트는 실행하지 않는다. 문서 계약과 렌더링 검증으로 범위를 증명한다.

## 버전과 출처 계약

매뉴얼의 공개 버전은 패치 버전을 묶은 마이너 버전 `0.2`다. 기술 설명의 기준은 최신 안정 배포본 `0.2.1`이며, 배포본과 작성 시점의 소스를 섞지 않는다.

| 항목 | 값 | 의미 |
|---|---|---|
| `stableVersion` | `0.2.1` | 사용자가 실제로 받는 최신 안정 버전 |
| `stableMinor` | `0.2` | 웹사이트와 URL에서 사용하는 매뉴얼 버전 |
| `releaseTag` | `0.2.1` | 안정 배포 태그 |
| `releaseRef` | `0.2.1` | GitHub 소스 링크의 기본 ref |
| `releaseCommit` | `2db7671afad20045afdcb5793c0113b8b23b972b` | 태그가 가리키는 실제 커밋 |
| 초기 작성 기준 | `2fef5c4bf65ae2865e0b03900f5ce7bbd24f2d8f` | 설계 시작 당시 `develop` 커밋 |

소스 저장소의 매뉴얼에는 안정 배포 근거를 `releaseCommit`으로 고정한다. 웹사이트가 매뉴얼을 가져갈 때는 위 값과 별도로 소스 PR이 병합된 최종 커밋을 `sourceCommit`으로 기록한다. 이 구분으로 “설명하는 라이브러리 버전”과 “문서를 작성한 소스 스냅샷”을 모두 재현할 수 있다.

버전 범위에 속하는 기술 주장과 소스 링크는 원칙적으로 `0.2.1` 태그를 사용한다. 작성 과정에서 `develop`의 자료를 참고할 수 있지만, `0.2.1`에 같은 기능이 있음을 확인하지 못한 내용은 공개 매뉴얼에 넣지 않는다.

## 문서 작성 계약

모듈·가이드·예제 문서는 가능한 한 다음 흐름을 따른다.

1. **사용자 문제**: 이 기능이 필요한 상황을 먼저 설명한다.
2. **가장 작은 유용한 예제**: 복사해 실행할 수 있는 코드와 기대 결과를 제시한다.
3. **동작 해석**: 결과가 나온 이유와 주요 API 계약을 실제 소스에 근거해 설명한다.
4. **선택 기준**: 다른 모듈이나 접근법과 비교해 언제 이 기능을 선택할지 말한다.
5. **주의점과 한계**: 초기화 비용, 입력 크기, 언어 혼합, 정확도, 동시성, 실패 조건을 숨기지 않는다.
6. **다음 학습 경로**: 관련 모듈, 실행 예제, 품질·운영 문서로 이어 준다.
7. **소스 근거**: 안정 태그의 구현, 테스트, 예제 또는 측정 자료를 링크한다.

학습 경로 문서는 링크 모음이 아니라 각 단계에서 배우는 개념, 실행할 예제, 확인할 결과, 다음 단계로 넘어갈 기준을 짧게 설명한다. 사용자가 상세 설명과 예제가 충분하다는 사실을 첫 화면에서 알 수 있어야 한다.

한국어 문서는 영어 문장의 어순을 그대로 옮기지 않는다. 주어를 불필요하게 반복하지 않고, 명사형 나열보다 자연스러운 서술문을 사용하며, “~할 수 있습니다”를 습관적으로 반복하지 않는다. API 이름과 정확한 기술 용어는 유지하되 문장 구조는 한국어 독자의 읽기 흐름에 맞춘다.

영어와 한국어 문서는 제목, 섹션, 예제, 제한 사항, 내부 링크, 근거 링크가 서로 대응해야 한다. 직역은 요구하지 않지만 어느 한쪽만 중요한 기술 정보를 갖는 것은 허용하지 않는다.

## 다이어그램 설계

최종 자산은 편집 가능한 SVG와 동일한 크기의 PNG를 함께 제공한다. 두 언어가 영어 레이블 자산을 공유한다.

| 자산 | 설명 |
|---|---|
| `assets/overview/repository-learning-map.svg/png` | 사용자 목표에서 모듈·가이드·예제로 이어지는 학습 지도 |
| `assets/architecture/capability-map.svg/png` | 언어 감지, 토큰화, 검색 기능과 모듈 경계 |
| `assets/architecture/text-processing-pipeline.svg/png` | 입력부터 감지·분기·토큰화·검색·결과까지의 처리 순서 |
| `assets/guides/language-detection-selection.svg/png` | Unicode 감지와 통계 기반 감지의 선택 흐름 |
| `assets/text-search/search-flow.svg/png` | 자동자 구성과 문자열·Flow 검색 경로 |
| `assets/operations/request-safety-boundary.svg/png` | 신뢰할 수 없는 입력, 제한, 처리기, 실패 격리 경계 |

시각 규칙은 다음과 같다.

- 승인된 매뉴얼 계열의 어두운 배경과 선명한 대비색을 사용한다.
- 기존 카드 구조를 유지하고, 굵은 왼쪽 강조선이나 불필요한 내부 구분선을 추가하지 않는다.
- 제목은 Architects Daughter, 코드·짧은 기술 레이블은 Comic Mono 계열을 사용한다.
- 화살촉은 축소된 PNG에서도 방향을 알아볼 수 있는 크기로 그린다.
- 연결선이 겹치거나 가까이 지나가면 서로 대비되는 색을 사용하고, 출발점과 도착점이 명확하도록 경로를 분리한다.
- 선은 카드 아래에 숨겨져도 실제 포트에 연결되어야 한다. 끊긴 선, 카드 내부를 가로지르는 선, 레이블과 겹치는 선은 허용하지 않는다.
- 텍스트는 카드 경계를 넘지 않아야 하며, 줄바꿈으로 의미 단위가 깨지면 카드 폭을 넓힌다.
- 장식보다 개념 관계를 우선하고, 한 그림에 너무 많은 책임을 넣지 않는다.

각 다이어그램은 체크리스트 검사와 전체 크기 눈 검수를 모두 통과해야 한다. 자동 검사만 통과했거나 축소판만 본 상태로 완료 처리하지 않는다.

## 매니페스트 계약

`docs/manual/manifest.yaml`은 스키마 버전 2를 사용하며 아래 정보를 가진다.

- `schemaVersion`, `repository`
- `stableVersion`, `stableMinor`
- `releaseTag`, `releaseRef`, `releaseCommit`
- `publication.manualVersion`, `publication.sourceRoot`, `publication.locales`, `publication.contentStatus`
- `overview.documents.en`, `overview.documents.ko`
- `overview.assets`
- `evidence`
- `modules`

`overview.documents`에는 언어별 24개 파일을 모두 명시한다. `overview.assets`에는 6개 SVG/PNG 쌍을 모두 기록한다. `modules`에는 BOM과 다섯 라이브러리 모듈을 넣고, 각 항목은 식별자, 다국어 제목, Gradle 경로, 프로젝트 이름, 소스 디렉터리, 종류, 그룹, Maven 좌표, 상태, 언어별 문서, 소스 경로를 제공한다. 예제 세 개는 문서 목록과 근거 목록으로 관리하되 배포 라이브러리 모듈로 오인되지 않게 한다.

검증된 JSON 산출물은 `docs/manual/generated/manifest.json`에 생성한다. 웹사이트는 임의로 디렉터리를 추측하지 않고 이 JSON과 고정된 `sourceCommit`을 사용해 문서와 자산을 가져간다.

검증은 다음 조건을 증명해야 한다.

1. 영어와 한국어 문서가 각각 정확히 24개이며 경로가 일치한다.
2. 내부 링크와 자산 링크가 존재하고 루트 밖으로 벗어나지 않는다.
3. 모듈, 예제, 근거 자료가 실제 릴리스 트리에 존재한다.
4. 안정 버전, 태그, 커밋, 마이너 버전 관계가 일관된다.
5. 공개 소스 링크가 `0.2.1` 범위와 맞는다.
6. SVG가 올바른 XML이며 PNG와 크기가 대응한다.
7. SVG 안의 텍스트, 카드, 연결선, 화살촉이 다이어그램 규칙을 만족한다.
8. PNG를 전체 크기로 열어 텍스트 넘침, 잘림, 겹침, 끊긴 연결선을 눈으로 확인한다.

11. `git diff --check`가 통과한다.

Ruby 테스트와 XML 검사 외에 CairoSVG 또는 저장소에서 채택한 동등 도구로 PNG를 렌더링한다. 문서 전용 변경이므로 Gradle/JVM 테스트는 **N/A**이며, `.kt`, 빌드 설정, 런타임 동작을 바꾸지 않았다는 diff가 그 근거다.
