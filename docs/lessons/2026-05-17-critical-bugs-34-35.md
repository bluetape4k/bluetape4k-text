## Bug #34 — Kotlin `init{}` Ordering Pitfall

### Root Cause

`EntryIterator` declared `init { goNext() }` before `private var pos = -1`.
Kotlin executes property declarations and `init {}` blocks in textual top-to-bottom order.
So `goNext()` ran while `pos` was still `0` (JVM int default), not `-1` as intended.
This caused the iterator to skip the very first map entry on every iteration.

### Fix

Move property declarations (`pos = -1`, `lastPos = 0`) above the `init {}` block.

### Key Lesson

**Kotlin `init {}` ordering is a silent correctness trap.**
Any `init {}` that calls a method depending on an instance property must have that property declared *above* the `init {}` block.
This is not enforced by the compiler — no warning is emitted.

Detection strategy: grep for `init {` followed by method calls, then check whether those methods read `var`/`val` properties declared below `init {}` in the same class body.

## Bug #35 — `runBlocking` Deadlock in Coroutine Context

### Root Cause

`KoreanChunker.chunk()` called `runBlocking(Dispatchers.Default)`, which blocks a thread from the Default dispatcher pool waiting for coroutines that also need Default dispatcher threads.
When `chunk()` is called from a coroutine already running on `Dispatchers.Default`, all threads in the pool can be occupied waiting for each other → deadlock.

### Fix

`splitBySpaceKeepingSpace` used `flow { emit() }` with only synchronous regex operations inside — no actual suspension.
Converting it to `sequence { yield() }` is a pure semantic equivalent that eliminates the coroutine dependency entirely.
`chunk()` then uses `.flatMap { }.forEach { }` — plain synchronous Sequence operations, no dispatcher interaction.

### Key Lesson

**`runBlocking` is not safe in production code on a shared dispatcher.**
It should only appear in tightly controlled contexts (lazy init, `main()`).

When a `flow { }` builder contains only synchronous operations (no `delay`, no `withContext`, no `suspend` calls), it can always be replaced with `sequence { yield() }` — same laziness, same semantics, zero coroutine overhead and no deadlock risk.

Pattern to avoid: `runBlocking(Dispatchers.Default) { coldFlow.collect { } }` — replace with `sequence` conversion or call from a dedicated thread pool.
