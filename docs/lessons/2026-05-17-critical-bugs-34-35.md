## 버그 #34 — Kotlin `init{}` 순서 함정

### 근본 원인

`EntryIterator`는 `private var pos = -1`보다 앞에 `init { goNext() }`를 선언했다.
Kotlin은 property declaration과 `init {}` block을 파일에 적힌 위에서 아래 순서대로
실행한다. 따라서 `goNext()`는 `pos`가 의도한 `-1`이 아니라 JVM int default인 `0`인
상태에서 실행됐다. 그 결과 iterator가 매번 첫 map entry를 건너뛰었다.

### 수정

Property declaration(`pos = -1`, `lastPos = 0`)을 `init {}` block 위로 이동했다.

### 핵심 교훈

**Kotlin `init {}` 순서는 조용한 correctness trap이다.**
Instance property에 의존하는 method를 호출하는 `init {}`는 해당 property를 반드시
`init {}` block보다 위에 선언해야 한다. Compiler는 이를 강제하지 않으며 warning도
내지 않는다.

탐지 전략: `init {` 뒤에 method call이 오는 위치를 grep한 뒤, 그 method가 같은 class
body에서 `init {}` 아래에 선언된 `var`/`val` property를 읽는지 확인한다.

## 버그 #35 — Coroutine context 안의 `runBlocking` deadlock

### 근본 원인

`KoreanChunker.chunk()`는 `runBlocking(Dispatchers.Default)`를 호출했다. 이는 Default
dispatcher pool의 thread를 block하면서, 동시에 Default dispatcher thread가 필요한
coroutine을 기다린다. `Dispatchers.Default`에서 이미 실행 중인 coroutine이 `chunk()`를
호출하면 pool의 모든 thread가 서로를 기다리며 점유되어 deadlock이 발생할 수 있다.

### 수정

`splitBySpaceKeepingSpace`는 `flow { emit() }`을 사용했지만 내부 작업은 동기 regex
operation뿐이었다. 실제 suspension이 없으므로 `sequence { yield() }`로 바꿔도 의미가
같고 coroutine dependency를 완전히 제거한다. 이후 `chunk()`는 `.flatMap { }.forEach { }`
같은 plain synchronous Sequence operation만 사용하므로 dispatcher interaction이 없다.

### 핵심 교훈

**`runBlocking`은 shared dispatcher 위의 production code에서 안전하지 않다.**
제어된 context(lazy init, `main()`)에서만 사용해야 한다.

`flow { }` builder가 동기 작업만 포함한다면(`delay`, `withContext`, `suspend` call 없음)
항상 `sequence { yield() }`로 대체할 수 있다. Laziness와 의미는 같고 coroutine overhead와
deadlock risk는 사라진다.

피해야 할 pattern: `runBlocking(Dispatchers.Default) { coldFlow.collect { } }`.
Sequence conversion으로 바꾸거나 dedicated thread pool에서 호출한다.
