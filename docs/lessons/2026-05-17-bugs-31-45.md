# Lessons: CharArrayMap.setValue no-op and UnmodifiableCharArrayMap aliasing

**Date:** 2026-05-17  
**Branch:** fix/bugs-31-45  
**Issues:** #31 (MapEntry.setValue no-op), #45 (UnmodifiableCharArrayMap undocumented aliasing)

---

## Bug #31 — MapEntry.setValue() was a no-op

### Root Cause

`MapEntry.setValue(newValue)` contained `_values[pos] = value` instead of `_values[pos] = newValue`.
The `value` property getter reads `_values[pos]` so this was a read-then-write-same-value no-op.
Any caller using the standard `MutableMap.MutableEntry.setValue` contract silently failed.

### Fix

Changed `_values[pos] = value` to `_values[pos] = newValue`.

### Key Lesson

Name shadowing between a property (`value`) and a parameter (`newValue`) is a common source
of subtle bugs. Code review should specifically check all assignments in `setValue` overrides.

## Issue #45 — UnmodifiableCharArrayMap aliasing was undocumented

### Root Cause

`UnmodifiableCharArrayMap` inherits `CharArrayMap(src: CharArrayMap)` which does a shallow
copy (shared backing arrays). This matches the `java.util.Collections.unmodifiableMap` contract
but was not documented, leaving callers unaware they must discard the original reference.

### Fix

Updated KDoc on `unmodifiableMap()` and `UnmodifiableCharArrayMap` to:
- Explicitly state the aliasing behavior (shared backing arrays)
- Show the correct usage pattern (discard original after wrapping)
- Reference the Java Collections precedent

### Key Lesson

Shared-backing read-only views are a standard Java pattern but require explicit KDoc.
Any wrapper that does not copy data must document the aliasing contract.
